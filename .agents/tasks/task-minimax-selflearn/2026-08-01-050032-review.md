# Minimax AI with self-learning weights and guide-dot bug fix

This change replaces the greedy position-weight COM strategy with a minimax search (alpha-beta pruning) at configurable depth (1/3/5 matching 初級/中級/上級 difficulty). A self-learning loop runs COM vs COM games off-screen, adjusting the position-weight table based on win/loss outcomes and persisting results to `learned_weights.json`. The guide-dot bug — yellow indicators appearing on incorrect squares — is fixed by removing a redundant `draw_placable()` call from `after_animation` and enabling `SHOW_GUIDE`.

Watch for: UI freeze during learning on the main thread (**confirmed**); learned weights only apply at 上級 difficulty, so 中級 plays with unlearned defaults despite minimax still being active (**confirmed**); the self-play loop uses identical weights for both sides, producing deterministic games that limit learning diversity (**likely**).

**Verdict**: NEEDS_CHANGES

## High-level view

The minimax engine is cleanly separated from the GUI: a set of `sim_*` functions operate on a plain 2D color array extracted from the board's dict-based cells, and the `Othello.com()` method delegates to `minimax()` instead of evaluating positions inline.

Self-learning runs synchronously on the tkinter main thread. While the button is disabled and a progress label updated, the event loop is only pumped every 10 games via `window.update()`. At depth 2 across 100 games this is likely tolerable (seconds), but the architecture does not gracefully degrade — increasing game count or depth will hard-freeze the window with no escape hatch.

Learned weights feed only into 上級 mode. 初級 and 中級 always use `DEFAULT_EVAL_WEIGHTS` regardless of whether a learned file exists. The self-learning feature has no observable effect unless the player selects 上級.

The guide-dot bug was caused by a double invocation of `draw_placable()`: once correctly inside `start_turn` and once incorrectly inside `after_animation` after `change_turn` had already mutated `self.player`. Removing the second call and adding `draw_placable()` to `reset_game` fixes both the false-positive dots and the missing dots on game start.

<summary>Issues (6)</summary>

1. **Main-thread learning freeze** — `start_learning_mode` runs the entire training loop synchronously on the tkinter main thread. Move the computation to a background thread (or use `after`-based chunking) so the window remains responsive and closeable.
2. **Deterministic self-play** — Both sides of a self-play game use the same weights at the same depth with no randomness, producing identical games after convergence. Inject noise (epsilon-greedy move selection or asymmetric depths) to maintain training diversity.
3. **Learned weights unused at 中級** — `get_com_weights` returns `DEFAULT_EVAL_WEIGHTS` for 初級 and 中級. If the intent is graduated difficulty, consider applying partial or dampened learned weights at 中級 so training benefits more than one level.
4. **Unbounded weight drift** — Weights are incremented/decremented by 0.5 per game with no clamping or decay. Over many training runs, values can drift arbitrarily far from the original distribution, potentially inverting corner advantages.
5. **Unused imports and dead global** — `import copy` is never used; `EVAL_WEIGHTS` (the mutable global copy) is defined but never referenced. Remove both.
6. **No file-write error handling in save** — `save_learned_weights` opens the file without a try/except; a permission error or full disk will crash the learning loop with an unhandled exception surfaced as a tkinter error dialog.

## Minimax engine separation

The `sim_*` family (`sim_get_reverse_list`, `sim_get_placable_list`, `sim_place`) duplicates the board-manipulation logic that already exists in `Othello` methods (`get_reverse_list`, `get_placable_list`), operating on a flat `[row][col] -> color|None` grid instead of the GUI's `{color, id}` dict. The duplication is a reasonable trade-off given that the GUI methods mutate canvas state and carry widget IDs — sharing them with headless simulation would require invasive refactoring. The cost is two parallel implementations of the same reversal logic that must stay in sync if the rules ever change.

## Self-play learning convergence problem

Both players in `self_play_game` call `minimax` with `maximizing=True` and the same `weights` table at the same depth (2). Because both sides see an identical evaluation landscape, the game is fully deterministic given a board state — the first game's outcome replays identically in all subsequent games unless the weight update from game N changes move ordering in game N+1.

In practice, early games do shift weights, causing subsequent games to diverge. But as weights stabilize, games converge to a fixed point — all 100 games replay the same sequence, hammering the same positions with +0.5/-0.5 adjustments each run. This is gradient descent trapped at a fixed point rather than exploring the strategy space.

A simple mitigation: with probability epsilon, choose a random move instead of the minimax-optimal one. This provides exploration and produces varied game outcomes even after convergence.

## UI responsiveness during learning

```python
def start_learning_mode():
    num_games = 100
    learn_btn.config(state="disabled")
    progress_label.config(text="学習中: 0/" + str(num_games))
    window.update()

    def progress_callback(current, total):
        progress_label.config(text=f"学習中: {current}/{total}")
        if current % 10 == 0:
            window.update()

    run_self_learning(num_games=num_games, progress_callback=progress_callback)
```

Between `window.update()` calls (up to 10 games apart), the UI is frozen — close button doesn't respond, the window cannot be moved or resized on some platforms. If `num_games` is later increased or depth raised above 2, each game takes longer and the freezes become user-visible. The standard fix is `threading.Thread` with a queue or `after`-based polling, ensuring the mainloop never blocks.

## Weight update semantics and drift

The learning rule is positional reinforcement: every square a winner touched gets +0.5, every square a loser touched gets -0.5. There is no normalization, clamping, or decay. Over multiple training sessions (the user can click "学習モード" repeatedly, each time loading saved weights and continuing), edge and interior values can drift to large magnitudes that make the mobility and endgame terms in `evaluate_board` irrelevant by comparison. Corner values growing large is mostly harmless, but if an interior cell drifts positive due to random win correlation, the AI will actively seek bad positions.

Clamping weights to a range (e.g., [-50, 50]) or applying multiplicative decay before each training batch would prevent runaway drift.

## Guide-dot bug fix

The original code:

```python
def after_animation(self):
    self.animating = False
    self.change_turn()          # mutates self.player via start_turn
    if self.player == YOU:      # checks AFTER mutation — but start_turn already drew guides
        self.draw_placable()
```

`change_turn()` → `start_turn(next_player)` already calls `draw_placable()` when the next player is YOU. The second call in `after_animation` was redundant at best and could fire guides at the wrong moment. The new code also adds `draw_placable()` at the end of `reset_game`, ensuring guides appear on the very first turn — previously invisible because `SHOW_GUIDE` was `False`.

## Learned weights gated to 上級 only

```python
def get_com_weights(self):
    ...
    if level == DIFFICULTY_ADVANCED:
        learned = load_learned_weights()
        if learned is not None:
            return learned
    return DEFAULT_EVAL_WEIGHTS
```

Difficulty levels differ only in search depth for 初級/中級, not evaluation quality. The self-learning feature is invisible unless the player selects 上級. If 中級 is meant to be noticeably stronger than 初級 beyond just look-ahead, applying dampened learned weights there would create a more perceptible gradient.

`load_learned_weights()` reads from disk on every COM move at 上級. The file is small (< 1KB), so latency is negligible, but mid-game changes to the file (e.g., another training run) immediately affect gameplay — loading once at game start would provide consistent behavior within a single game.
